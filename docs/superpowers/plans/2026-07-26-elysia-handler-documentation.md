# Elysia Handler Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require complete English OpenAPI documentation and examples for every Elysia handler, input, and declared response.

**Architecture:** A small `apiOperation` helper owns required operation metadata while Elysia continues generating `operationId` from method and path. TypeBox schema factories expose documented envelope fields and route-specific response examples. A source architecture rule covers hidden handlers; an OpenAPI contract validator checks every visible generated operation.

**Tech Stack:** Bun, TypeScript, Elysia, TypeBox, `@elysia/openapi`, Bun test.

## Global Constraints

- Every handler in `apps/api/src/routes` uses `apiOperation({ summary, description, tags })`; hidden handlers add `hide: true` through that helper.
- `operationId` remains generated by `@elysia/openapi`; do not set it manually.
- All operation, parameter, schema-field, and response descriptions are non-empty English text.
- Every documented input field and response field has at least one example, except the route-local documented `t.Any()` worker body exemption.
- Every declared response status has a description and an `application/json` example.
- Existing HTTP behavior, versioning, and hidden internal-route behavior remain unchanged.
- `.agent/api/README.md` documents the standard and `task quality` rejects violations.

```ts
test("builds documented operation detail", () => {

		apiOperation({ summary: "Get API status", description: "Returns the current status of the versioned public API.", tags: ["System"] }),
```
